# 設計ドキュメント

## 1. 目的とスコープ

野球の試合動画から、スコア収集(最終的にはスコアブック相当のデータ)を **半自動** で行う。
完全自動は目指さない — 決定的アルゴリズムと LLM で候補データを作り、最終確認は人間が行う前提。

### v1 のスコープ

- **対象動画**: 画面内にスコアボード(球場の電光掲示板 or 放送のスコア表示)が映っている動画
- **抽出データ**: イニングごとの得点、B/S/O カウント、ランナー状況の時系列
- **スコープ外(将来)**: スコアボードが映っていない動画からのプレー認識、選手個人成績、配球

## 2. 設計原則

1. **ホワイトボックス優先**: 決定的に解ける処理(分割・検出・OCR・ルール検証)はコードで実装する。
   再現性があり、無料で、デバッグ可能だから。
2. **LLM は「曖昧さの解決」専用**: OCR の信頼度が低いフレーム、ルール上ありえない状態遷移、
   「この 2 状態の間で何が起きたか」の推定にだけ使う。API コストとレイテンシを最小化する。
3. **野球ルールを検証器として使う**: 得点は減らない、アウトは 0→1→2→チェンジ、B は 0-3、S は 0-2 …
   これらの制約で OCR の誤読を機械的に検出できる。これが本システムの肝。

## 3. パイプライン詳細

### Stage 1: フレーム抽出(ffmpeg)

- `ffprobe` でメタデータ取得(長さ・解像度・fps)
- 固定間隔サンプリング(デフォルト 1 fps)。スコアボードの変化は秒単位なので十分
- 長い動画はセグメント分割して並列処理可能な構造にする

### Stage 2: シーン分割(OpenCV)

- 隣接フレームのヒストグラム差分でカット検出
- リプレイ・CM・ベンチ映像などスコアボードが消える区間の識別に使う

### Stage 3: スコアボード領域検出(OpenCV)

- **原理**: スコアボード/スコアバグは画面上の位置が固定で、背景より時間変化が小さい。
  フレーム集合の画素ごとの時間方向分散を取り、低分散かつエッジ密度が高い矩形領域を候補にする
- 一度検出した領域は動画全体でキャッシュ(カメラ固定前提。放送のスコアバグも位置固定)
- 検出失敗時は LLM に代表フレームを渡して領域を尋ねるフォールバックあり

### Stage 4: OCR(Tesseract)

- 検出領域をクロップ → 二値化・拡大などの前処理 → 数字ホワイトリストで OCR
- 出力: `ScoreboardReading`(得点、イニング、B/S/O、信頼度スコア)

### Stage 5: ルール検証(状態機械)— `rules.py`

読み取り結果の時系列に対して野球ルールの制約を適用する:

| 制約 | 内容 |
|---|---|
| 得点単調性 | 各チームの得点は減少しない |
| カウント範囲 | B∈[0,3], S∈[0,2], O∈[0,2] |
| カウント遷移 | B/S は 1 ずつ増えるかリセット。O は増えるかチェンジでリセット |
| イニング進行 | 順方向にのみ進む。表→裏→次の回の表 |
| 得点とイニングの整合 | 攻撃側チームの得点のみ増加しうる |

違反した読み取りは「疑わしい」とマークされ、Stage 6 へ回る。
**このステージは純粋関数のみで構成され、ユニットテストで完全に検証できる。**

### Stage 6: LLM フォールバック(Claude Vision)

- 疑わしいフレームのクロップ画像を Claude に渡し、構造化出力(JSON Schema)で読み取らせる
- 前後の確定済み状態をコンテキストとして与える(「直前は 2アウト 3-2 でした」)
- モデル: `claude-opus-5`(視覚+推論)。構造化出力で `ScoreboardReading` スキーマを強制

### Stage 7: プレー推定(Claude)

- 確定した状態遷移の差分(例: 2アウト→0アウト+得点2追加+イニング進行)を Claude に渡し、
  「何が起きた可能性が高いか」(2点タイムリー後にチェンジ、等)を候補として生成
- 出力はあくまで **候補**。人間のレビューで確定する

## 4. データモデル

```
GameState:
  inning: int          # 1〜
  top: bool            # 表 = True
  balls, strikes, outs # カウント
  score_home, score_away
  runners: (一塁, 二塁, 三塁) の bool

ScoreboardReading:      # OCR / LLM の生読み取り
  timestamp: float      # 動画内秒数
  state: GameState
  confidence: float     # 0.0-1.0
  source: "ocr" | "llm"

PlayEvent:              # Stage 7 の出力候補
  from_state, to_state, timestamp_range
  description: str      # 「レフト前ヒットで2者生還、その後三振でチェンジ」
  confidence: float
```

## 5. コスト・性能の見積もり

- 2 時間の試合 @ 1fps = 7,200 フレーム。スコアボードクロップの OCR は 1 フレーム数十 ms → 数分で完了
- LLM 呼び出しは疑わしいフレームのみ。経験則で全体の 1〜5% 程度を想定(数十〜数百コール)
- クロップ画像は小さい(数百 px)ので 1 コールあたりの入力トークンは少ない
